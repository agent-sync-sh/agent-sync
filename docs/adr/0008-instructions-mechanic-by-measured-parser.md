# An instructions mechanic is assigned by measured parser behavior, and a symlink is refused where another tool rewrites the file

v1 gave every agent but Claude a symlink for `AGENTS.md`, and the Claude comment explained its import line by ownership alone ("users keep their own content in `CLAUDE.md`"). Both rationales were incomplete. A symlink is unsafe wherever another tool rewrites the agent's instructions file with a plain `writeFileSync`, because the write follows the link into the Commons and the hourly fleet sync then carries the pollution everywhere (claude-mem 13.25.1 did exactly this through `~/.config/opencode/AGENTS.md` on every session and through `~/.gemini/GEMINI.md` once). And an import line is only a mechanic where the agent is *measured* to expand it: an unparsed `@path` leaves the agent with no instructions and no error, which is indistinguishable from working. So the registry now assigns each agent's mechanic from evidence, recorded here so it can be re-measured when an agent ships a new parser.

| agent | build measured 2026-09-18 | import line | symlink at its instructions path | mechanic |
|---|---|---|---|---|
| codex | 0.155.0 | not expanded — `codex debug prompt-input` shows the `@` line verbatim in the prompt and the imported sentinel absent; upstream openai/codex#6038 and #17401 both open | safe — claude-mem's Codex writer is strip-only and returns early unless both context tags are present | **Symlink** (unchanged) |
| opencode | 1.18.31 | no `@` syntax at all (docs/rules) | **unsafe** — `injectContextIntoMarkdownFile` writes unconditionally on every session | **Include-entry** on the `instructions` array in `opencode.json` |
| gemini | Homebrew 0.46.0 on all six fleet hosts (macbook-air's two mise packages are inert; its PATH `gemini` is a mise shim for an inactive tool, and the login shell runs the Cellar binary) | refused — `validateImportPath` is lexical `path.resolve` against `[projectRoot]`, `projectRoot` falls back to `~/.gemini` itself when no `.git` is found walking up, so every home-level target is a "Path traversal attempt"; no `~` expansion on that path | **unsafe** — `setupGeminiMdContextSection` writes once when its tag is absent | **Include-entry** on `context.fileName` in `settings.json` |

**Why Include-entry.** Both agents list the instruction files they load in a config file agent-sync already key-merges into. One entry naming the Commons `AGENTS.md`, owned by element identity exactly as a hook is (ADR-0003), keeps the single-file property of ADR-0001: the Commons is still the only real copy, nothing is rendered, no state is needed, and another tool's block lands in that tool's own file. opencode expands `~/` itself and globs an absolute entry by basename in its directory (`instruction.ts`), and its glob matches a Commons file that is itself a symlink, so a Sourced Commons still works. Gemini joins every configured name under `~/.gemini`, checks each with `fs.access`, and loads all that pass, so `../.agents/AGENTS.md` resolves to the Commons and loads as global memory. A name that does not resolve is kept and simply skipped (`robustRealpath` synthesizes a path on `ENOENT`), which the peer session confirmed by driving the deployed loader from a scratch `GEMINI_CLI_HOME`: no startup throw from a non-resolving cwd, both files loaded.

**Ordering is load-bearing for Gemini.** `setGeminiMdFilename` unions the configured names with the current list, new entries first, and element 0 is the `save_memory` write target and the ignore pattern. Written as `["GEMINI.md", "../.agents/AGENTS.md"]`, memories keep landing in `GEMINI.md`; reversed, Gemini would write memories into the shared Commons. agent-sync therefore appends and never inserts first, and a user array that already has the Commons at index 0 is reported as a conflict, not reordered.

## Considered and rejected

- **Import line for all three** (the fleet request that started this): fails silently on every one of them, per the table.
- **Symlink placed inside `~/.gemini` and imported by a relative name**: works on the deployed 0.46.0 because the validator is lexical, and dies on upstream `ff00dac` (2026-07-01, google-gemini/gemini-cli#28233, shipped in v0.51.0 and later), which realpaths both sides. Five hosts are Homebrew-pinned at the same version and would cross that boundary together on one `brew upgrade`, with the only symptom an `<!-- Import failed -->` comment inside a file nobody reads at runtime. A version gate cannot see this; a capability probe would have to spawn Gemini on every sync.
- **`context.includeDirectories: ["~/.agents"]`**: loads the Commons, but also makes `~/.agents` a full read/write workspace root for the model's file tools and passes it to the sandbox.
- **`context.memoryBoundaryMarkers: [".git", ".agents"]` plus an import line**: two edits, one to a file claude-mem writes, and the import still dies on `ff00dac`.
- **Rendered copy with a Marker**, agentsync's answer (its `renderMemory` writes the canonical body into each agent's file behind a state-hash drift classifier): the copy absorbs another tool's writes harmlessly, but only by the ownership tracking ADR-0001 refused, and it would fight the hourly `sync-agentsmd` push. Kept as the honest fallback for an agent that has neither a usable import nor a config list.

## Consequences

- Import-line's glossary claim narrows from "the sole sanctioned edit to a user file outside MCP rendering" to "the sole sanctioned edit to a user's *prose* file"; Include-entry is the sanctioned edit to a config file's list.
- `sync` removes a legacy Commons symlink at an Include-entry agent's old instructions path, as it prunes Codex's legacy skills links, and never touches a real file there; the path is no longer a destination, so a real file there is no longer a Conflict.
- `doctor` warns when an import line naming the Commons sits in a file whose agent is not on the Import-line mechanic: that line is inert, and this ADR is why.
- Re-measure when Codex closes #6038/#17401 (an import line becomes possible, though the symlink stays correct), when claude-mem changes its writers (the symlink hazard may close for opencode or gemini), or when Homebrew ships gemini-cli 0.51.0 or later (nothing here breaks, but the rejected routes change shape).
